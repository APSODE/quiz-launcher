# 문제 실행기 v2 설계

웹 앱 + 백엔드로 바꾸고, 친구들(10~20명)이 함께 쓰는 버전의 설계 문서다. 논의(2026-11-09)에서 정한 내용을 정리했고, 아직 구현 전이다.
기존 형식 명세는 `quiz_format_spec.md`, 문제 생성 흐름은 `GENERATE.md`가 기준이며 이 문서는 그 둘을 바꾸지 않는다(바뀌는 곳은 12장에 모아 둔다).

## 0. 목표와 범위

**목표**
- 브라우저로 접속해 로그인하고, 문제 풀이 · 오답 분석 · 단어 암기 · 연습 메뉴를 지금처럼 쓴다.
- 친구들의 풀이 결과를 모아 리더보드로 보여 준다.
- 과목별로 오늘 복습할 문제를 골라 준다(SRS).
- 친구들이 JSON으로 문제 세트를 올리고, 관리자가 승인하면 레포에 반영된다.
- 문항 신고와 문항별 댓글.

**바꾸지 않는 것**
- 커밋 흐름: `GENERATE.md`의 생성 · 검토 · 커밋 단계, pre-commit 훅(`tools/hooks/pre-commit`), `tools/check.js` · `tools/os-calc.js`.
- 문제 폴더 구조와 JSX 형식(`<과목>/{일반문제,모의고사,기출,단어집}/*.jsx`, `플러그인/`, `<과목>/연습/`). META에 `uploader` 필드 하나만 추가한다.
- git 레포가 문제 내용의 유일한 원본이다. DB에는 문제 내용을 저장하지 않는다(승인 대기 중인 업로드만 예외).

**하지 않는 것**
- `file://`로 여는 방식(묶음 파일 · 폴더 불러오기 · 끌어다 놓기). 새 앱은 서버로만 연다.
- AI 기능, 과목별 접근 제한, 리더보드 필터(기간 · 과목).
- 기존 연습 플러그인 11개 재작성. 호환 계층으로 그대로 돌린다(중간고사용이라 이후 사용 빈도가 낮다).
- 호스팅 · 배포 구성. 서버는 운영자가 직접 올린다. 이 문서는 빌드 결과물과 환경 변수만 정한다(15장).

## 1. 결정 사항 요약

| 영역 | 결정 |
|---|---|
| 실행 방식 | 정적 웹 앱 + API 서버. `file://` 지원 중단 |
| 기술 | TypeScript 모노레포. 웹은 Preact + Vite, 서버는 Hono(Node) + SQLite |
| 사용자 | 초대 링크로 각자 가입. 권한은 `admin`(운영자 1명)과 `member` |
| 기록 반영 | 세트를 끝까지 푼 세션(또는 복습 세션)만 리더보드 · SRS에 반영 |
| 리더보드 | 푼 문제 수 = 서로 다른 문항 수, 정답률 = 맞힌 횟수 / 전체 풀이 횟수. 필터 없음 |
| 복습(SRS) | FSRS. 완료한 세트의 문항만 대상, 과목 · 시험별, 하루 제한 없음. 복습 세션도 리더보드에 반영 |
| 문항 ID | 기존 기록 키(`weakQKey`)와 같은 해시 규칙 + 선택적 고정 `id` + 별칭 테이블 |
| 업로드 | JSON만. 파일 하나 = 세트 하나, 여러 파일을 한 번에. 서버 검사 → 관리자 승인 → `.jsx`로 변환해 커밋 |
| 메뉴 | 학년 → 학기(1 · 2) → 시험(중간고사 · 기말고사) → 과목. 학년 · 학기는 `과목목록.json`, 시험은 세트 META의 `exam`(3.4) |
| 과목 표시 | 사용자별 설정으로 과목 숨김 · 표시. 기본은 표시 |
| 새 과목 | 승인된 JSON의 과목이 처음이면 자동으로 과목이 생긴다(모두에게 표시) |
| 세트 카드 | 업로드한 세트에는 올린 사람 닉네임 표시 |
| 같이 쓰는 기능 | 문항 신고, 문항별 댓글(채점 후에만 보임) |
| 기존 기록 | GitHub `logs/*.jsonl` 기록은 운영자가 요청할 때 운영자 계정으로 옮긴다(16장) |

## 2. 전체 구조

```
quiz-launcher/
├─ 운영체제/ 웹프로그래밍/ 컴퓨터네트워크/ …   문제 내용 (그대로)
├─ 플러그인/                                   연습 메뉴 플러그인 (그대로)
├─ 과목목록.json                               과목별 학년 · 학기 (3.4)
├─ v1/                                         옛 실행기 quiz_launcher.html · quiz_bundle.js · build-bundle.js (유지 안 함, v2 와 충돌하면 v2 우선)
├─ tools/                                      check.js · jsx-parser.js(기준 파서) · os-calc.js · hooks/
├─ packages/core/       파서 · 스키마 · 채점 · 문항 ID · FSRS 계산 · 업로드 변환
├─ apps/web/            Preact + Vite → 정적 파일(dist/)
├─ apps/server/         Hono API + SQLite + 콘텐츠 로더 + git 작업
├─ docs/                설계 문서
├─ package.json · pnpm-workspace.yaml · tsconfig.base.json
```

```
 브라우저 (apps/web 정적 파일)
   │  /api/*  (세션 쿠키)
   ▼
 API 서버 (apps/server) ──── SQLite (계정 · 풀이 · SRS · 업로드 대기 · 신고 · 댓글)
   │  읽기: 콘텐츠 로더 (core 파서)
   │  쓰기: 승인된 업로드 → git commit · push (기존 훅 실행)
   ▼
 콘텐츠 작업 사본 (이 레포를 clone 한 폴더)  ⇄  GitHub 원격
```

- `packages/core`는 브라우저와 Node 양쪽에서 돈다(DOM · `fs` 사용 금지). 웹 · 서버 · `tools/check.js`가 같은 코드를 쓴다.
- 패키지 관리는 pnpm workspace. 주요 라이브러리: `preact`, `@preact/signals`, `vite`, `hono`, `@hono/node-server`, `better-sqlite3`, `drizzle-orm`, `zod`, `ts-fsrs`, `@node-rs/argon2`, 테스트는 `vitest`.

## 3. 콘텐츠 제공

### 3.1 콘텐츠 로더 (서버)

- 서버는 설정된 경로(`CONTENT_DIR`)의 작업 사본을 읽는다. 폴더 규칙은 `quiz_format_spec.md` 11장과 같다.
- 시작할 때와 새로고침 때 전체를 다시 읽는다. 새로고침은 먼저 `git pull --ff-only`를 한다. 새로고침이 일어나는 경우는 셋이다.
  1. **GitHub webhook**(기본): 원격에 push가 들어오면 바로 반영된다(3.2).
  2. 업로드 승인 커밋 직후(8.3).
  3. 관리자 "콘텐츠 새로고침" 버튼(`POST /api/admin/content/reload`). webhook이 실패했을 때 쓰는 예비 수단이다.
- 문제 세트 · 용어집은 core 파서로 읽어 **파싱된 JSON**으로 메모리에 들고 있는다. 브라우저는 JSX를 파싱하지 않는다.
- 플러그인(`플러그인/**/*.js`)과 연습 문항 데이터(`<과목>/연습/**/*.jsx`)는 코드로 실행되므로 서버가 평가하지 않고 **원문 그대로** 내려 준다. 실행은 브라우저의 호환 계층(10.3)이 한다.
- 매니페스트: 학년 → 학기 → 시험 → 과목 트리(3.4), 과목 · 시험별 세트 목록(경로, 분류, 제목, unit, topic, 문항 수, 유형별 수, uploader, 해시)과 용어 수, 플러그인 · 연습 데이터 목록. 버전(`contentVersion` = 전체 해시)을 함께 준다. 브라우저는 버전이 바뀐 경우에만 다시 받는다.
- 새 과목은 매니페스트에 과목 폴더가 생기는 순간 자동으로 나타난다(별도 등록 없음). `과목목록.json`에 없으면 "미분류"에 나온다.
- 묶음 파일(`v1/quiz_bundle.js`)은 v1 전용이다. 훅은 만들지 않고 새 앱도 쓰지 않는다(필요하면 `node v1/build-bundle.js`).

### 3.2 GitHub webhook

- 엔드포인트: `POST /api/webhooks/github`. GitHub 레포 설정에서 Payload URL = `<PUBLIC_ORIGIN>/api/webhooks/github`, Content type = `application/json`, Secret = `GITHUB_WEBHOOK_SECRET`, 이벤트 = `push`만.
- 검증: `X-Hub-Signature-256`을 요청 본문 원문과 시크릿의 HMAC-SHA256으로 계산해 상수 시간 비교한다. 다르면 401. 로그인 · `Origin` 검사 대상에서 빠지는 유일한 변경 요청이다.
- 처리
  - `ping` 이벤트는 200만 돌려준다. `push`가 아닌 이벤트와 `ref`가 `refs/heads/<CONTENT_BRANCH>`가 아닌 push는 무시한다(200).
  - push의 `after` 커밋이 이미 작업 사본의 `HEAD`면(서버가 승인하며 만든 커밋 등) 다시 읽지 않는다.
  - 그 밖에는 바로 202를 돌려주고 비동기로 `git pull --ff-only` → 콘텐츠 새로고침을 한다(GitHub는 10초 안에 응답을 기다린다).
  - 같은 `X-GitHub-Delivery` ID는 한 번만 처리한다(최근 100개 기억).
- git 작업(webhook pull, 승인 커밋 · push, 수동 새로고침)은 서버 안의 **잠금 하나로 순서대로** 실행한다. 승인 커밋 도중에 webhook이 오면 끝난 뒤 pull한다.
- pull이 실패하면(작업 사본에 커밋하지 않은 변경, fast-forward 불가 등) 콘텐츠는 이전 상태로 두고, 관리자 화면에 경고(시각 · 커밋 · git 출력)를 띄운다. 마지막 webhook 수신 시각과 결과도 관리자 화면에 보인다.
- 브라우저는 매니페스트의 `contentVersion`을 화면 이동 때 확인하므로(5분 캐시), push하고 나서 길어야 몇 분 안에 새 세트가 보인다.

### 3.3 파서 이전 (core)

- `quiz_launcher.html`의 `sliceBalanced` ~ `parseJSX`와 유형 판별 · 정규화(단답 `answer` → `answers` 등)를 `packages/core/src/parse/`로 옮긴다.
- **골든 테스트**: 레포의 모든 문제 파일을 기존 파서(HTML에서 꺼낸 것)와 core 파서로 각각 읽어 결과가 같은지 비교한다. 같아야 이전을 끝낸 것으로 본다.
- 그 뒤 `tools/check.js`는 HTML에서 꺼내는 대신 core 빌드 결과를 쓴다. 출력 · 종료 코드 · 옵션은 그대로 둔다(훅과 GENERATE.md가 의존).

### 3.4 학년 · 학기 · 시험 분류

메뉴는 **학년 → 학기 → 시험 → 과목** 순서로 들어간다. 폴더 구조는 바꾸지 않고 메타데이터로 정한다(폴더를 바꾸면 GENERATE.md 경로 · check.js · 훅 · 묶음 파일 · 플러그인 경로가 모두 바뀌기 때문).

- **학년 · 학기 = 과목 정보**: 레포 루트의 `과목목록.json`.
  ```json
  [
    { "subject": "운영체제", "grade": 2, "semester": 2 },
    { "subject": "웹프로그래밍", "grade": 2, "semester": 2 },
    { "subject": "컴퓨터네트워크", "grade": 2, "semester": 2 }
  ]
  ```
  - `grade`: 1 이상의 정수(학년). `semester`: `1` 또는 `2`. 계절학기는 없다.
  - 과목 하나에 항목 하나. 과목명은 과목 폴더 이름과 정확히 같아야 한다.
  - 목록에 없는 과목은 학년 단계 맨 끝의 **미분류** 아래에 나온다(시험 단계는 그대로 거친다).
- **시험 = 세트 정보**: 문제 세트와 용어집 파일의 META에 `exam: "중간고사"` 또는 `exam: "기말고사"`.
  - 문제 파일 안의 TERMS는 그 파일의 시험에 속한다. 용어집은 **시험별로** 나뉜다(용어 확인 · 단어 암기 테스트는 고른 시험의 용어만 쓴다).
  - `exam`은 필수다. 기존 파일은 전부 중간고사용이므로 한 번에 `exam: "중간고사"`를 넣는다(아래 이전 작업).
- **트리 만들기**: 서버가 세트마다 (과목의 학년 · 학기, 세트의 시험)으로 자리를 정한다. 세트가 하나도 없는 시험은 그 과목 아래에 만들지 않는다. 사용자가 숨긴 과목(10.4)을 빼고 남는 것이 없는 단계는 통째로 보이지 않는다.
- **이전 작업(한 번)**: 스크립트로 기존 문제 · 용어집 파일 META에 `exam: "중간고사"`를 넣고(META가 없는 파일은 META 줄을 만든다), 위 `과목목록.json`(현재 세 과목 모두 2학년 2학기)을 만들어 커밋 하나로 반영한다. 기존 커밋 흐름(훅 검사 포함)으로 커밋한다. 기존 실행기는 모르는 META 필드를 무시하므로 계속 동작한다.

## 4. 문항 ID

리더보드 · SRS · 신고 · 댓글이 모두 문항 ID를 기준으로 하므로 바뀌지 않는 것이 중요하다.

- **기본 ID** = `<세트 경로>#<해시>`. 해시는 기존 `weakQKey`와 같은 규칙(질문 글에서 공백을 모두 지우고 djb2, 36진수)이다. 기존 기록과 맞추기 위해 일부러 같게 둔다.
  - 세트 경로는 콘텐츠 루트 기준 상대 경로(NFC). 예: `운영체제/일반문제/운영체제_4장_스케줄링_OX_20문제.jsx#1x2k3m`
  - 파일 안에서 문항 순서를 바꿔도 ID는 그대로다. 질문 글을 고치거나 파일을 옮기면 바뀐다.
- **고정 ID**: 문항에 `id` 필드(문자열)가 있으면 ID = `id:<값>`. 업로드 문항은 승인할 때 서버가 `u<base36 시각><랜덤 4자>`를 붙인다. 기존 문항에는 붙이지 않는다.
- **별칭**: ID가 바뀐 문항은 `item_aliases(old_id → new_id)`로 잇는다. 모든 집계는 별칭을 따라간 최종 ID로 한다.
  - 콘텐츠 새로고침 때 서버가 이전 매니페스트와 비교해, 같은 파일에서 사라진 문항과 새로 생긴 문항을 질문 글 유사도(core의 2-gram, `check.js --dup`과 같은 계산) 0.6 이상이면 **별칭 후보**로 만든다.
  - 관리자 화면에서 후보를 확인하면 별칭이 확정된다. 확정 전에는 옛 ID의 기록이 그대로 남아 있을 뿐 사라지지 않는다.
- 같은 세트에 같은 ID가 두 개 생기면(질문 글이 같음) `check.js`가 이미 "같은 파일 안 중복 문제"로 잡는다.

## 5. 풀이 기록 모델

### 5.1 세션

- 풀이 단위는 **세션**이다. 종류는 `set`(세트 하나를 처음부터 끝까지), `review`(SRS 복습), `partial`(틀린 문제 다시 풀기 · 모아 풀기 · 📌 목록 풀기).
- 브라우저는 세션 동안 답을 모았다가 **끝까지 풀었을 때 한 번에** 서버로 보낸다. 중간에 그만둔 세션은 보내지 않는다(기존 실행기와 같은 규칙).
- 보낼 때는 학생이 입력한 원래 답(OX 값, 보기 번호, 단답 문자열)을 보낸다. **서버가 core 채점기로 다시 채점**해서 저장한다. 화면의 즉시 채점도 같은 core 채점기라 결과가 같고, 브라우저에서 결과를 조작해도 반영되지 않는다.
- 서버의 완료 판정
  - `set`: 보낸 문항 ID 집합이 그 세트의 현재 문항 전부와 같아야 한다. 세트 해시가 바뀐 뒤에 보낸 세션이면 남은 문항 기준으로 판정하고, 없어진 문항의 답은 버린다.
  - `review`: 서버가 발급한 복습 목록(7장)의 문항을 전부 답해야 한다.
  - `partial`: 완료 판정 없이 받는다.
- 오프라인이거나 전송에 실패하면 브라우저의 대기열(localStorage)에 두고 다시 보낸다. 세션마다 브라우저가 만든 `client_session_id`(UUID)가 있어 같은 세션이 두 번 저장되지 않는다.

### 5.2 반영 규칙

| 반영처 | `set` | `review` | `partial` |
|---|---|---|---|
| 리더보드 | O | O | X |
| SRS | O | O | X |
| 오답 분석 · 세트별 기록 | O | O | O (문항별 통계만, 세트별 점수 기록은 제외) |

- `partial`은 기존 실행기에서도 세트별 점수에서 빠지고 문항 통계에는 들어간다. 그 동작을 유지한다.
- 연습 메뉴(플러그인)와 단어 암기 테스트는 기록하지 않는다(기존과 같음).

### 5.3 기존 기록 기능 대응

| 기존 (`quizLauncher.weak`) | v2 |
|---|---|
| 장 · 범위 · 문제 · 세트별 오답 통계 | 서버 `session_answers`에서 사용자별 · 과목 · 시험별로 계산 (`GET /api/me/analysis`) |
| 📌 다시 풀 목록 (`pick`) | `pinned_items` 테이블 |
| 기록 지우기 (`reset`) | 과목 기준으로 그 사용자의 오답 분석 기준 시각을 옮긴다(`analysis_resets`). 리더보드 · SRS는 지우지 않는다 |
| GitHub 기록 동기화 | 없앤다. 서버가 기록을 저장한다 |
| 단축키 설정 | 기기별 설정이라 localStorage에 그대로 둔다 |

## 6. 리더보드

- 하나의 표. 열은 순위 · 닉네임 · 푼 문제 수 · 정답률 · (참고) 풀이 횟수. 정렬 기준을 **푼 문제 수 / 정답률** 중에서 고른다. 기간 · 과목 필터는 없다.
- 계산 대상: `set` · `review` 세션의 답 전부(5.2).
  - **푼 문제 수** = 서로 다른 문항 수(별칭 해소 후 최종 ID 기준). 같은 문항을 여러 번 풀어도 1.
  - **정답률** = 맞힌 횟수 / 전체 풀이 횟수. 같은 문항을 다시 풀면 다시 들어간다.
- 정렬이 같으면 다른 지표, 그다음 가입 순.
- 풀이 기록이 없는 사용자는 표에 넣지 않는다. 정지된 계정은 빠진다.
- 콘텐츠에서 사라진 문항(삭제된 세트)의 기록도 그대로 센다. 이미 푼 기록이기 때문이다.
- 인원이 적으므로 요청 때마다 SQL로 집계한다(인덱스: `session_answers(user_id, item_id)`).

## 7. 복습 (SRS)

- 알고리즘: FSRS(`ts-fsrs`). 계산은 core에 두고 서버가 실행한다.
- **카드 생성**: `set` 세션을 완료하면 그 세트의 문항마다 카드가 생긴다(없을 때만). 완료하지 않은 세트의 문항은 복습 대상이 되지 않는다.
- **평가**: 맞으면 `Good`, 틀리면 `Again`. 응답 시간 등으로 `Hard` · `Easy`를 나누지 않는다.
- **갱신**: `set` · `review` 세션의 답마다 순서대로 카드를 갱신한다. 이미 완료한 세트를 다시 풀어도 갱신된다.
- **오늘의 복습**: 과목 화면의 "🔁 오늘의 복습 (N문항)". `due ≤ 지금`인 카드 전부를, 늦은 순(오래 밀린 것 먼저)으로 낸다. 하루 개수 제한 없음. **과목 · 시험별로** 연다(고른 시험의 세트에서 나온 문항만). 과목이나 시험을 섞지 않는다. 문항의 시험은 그 문항이 속한 세트의 `exam`으로 정한다.
- 복습을 시작하면 서버가 그 시점의 목록을 `review_batches`로 발급한다. 전부 풀어야 완료이며, 완료하면 리더보드와 SRS에 반영된다(5.2).
- 콘텐츠에서 사라졌거나 별칭이 확정되지 않은 옛 ID의 카드는 복습 목록에서 뺀다. 별칭이 확정되면 카드가 새 ID로 옮겨진다.
- 문항 화면은 일반 풀이 화면을 그대로 쓴다(유형별 입력 · 해설 · 단축키 동일).

## 8. 문제 업로드

### 8.1 업로드 JSON 형식

파일 하나 = 세트 하나. 기존 JSX의 META · 문제 · 용어 형식을 JSON으로 옮긴 것이고, 문항 필드는 `quiz_format_spec.md` 4~5장과 같다.

```json
{
  "meta": {
    "subject": "운영체제",
    "grade": 2,
    "semester": 2,
    "exam": "중간고사",
    "kind": "일반문제",
    "title": "스케줄링 OX 20문제",
    "unit": "4장",
    "topic": "선점 · 비선점"
  },
  "questions": [
    { "category": "스케줄링", "question": "FCFS는 선점형 스케줄링이다.", "answer": false,
      "explanation": "FCFS는 비선점형이다." },
    { "category": "교착상태", "question": "교착상태의 필요조건이 아닌 것은?",
      "choices": ["상호 배제", "점유와 대기", "선점", "환형 대기"], "answer": 2,
      "explanation": "필요조건은 비선점이다." },
    { "category": "스케줄링", "question": "작업시간이 가장 짧은 프로세스를 먼저 실행하는 비선점 스케줄링은?",
      "answers": ["SJF", "최단 작업 우선", "최단작업우선"], "displayAnswer": "SJF",
      "explanation": "SJF는 평균 대기시간이 가장 짧다." }
  ],
  "terms": [
    { "terms": ["SJF", "최단 작업 우선"], "group": "4장", "desc": "작업시간이 가장 짧은 프로세스를 먼저 실행하는 비선점 스케줄링" }
  ]
}
```

- `meta.subject`(필수): 과목명. 기존 과목과 한 글자라도 다르면 새 과목이 된다.
- `meta.exam`(필수): `중간고사` 또는 `기말고사`.
- `meta.grade` · `meta.semester`: `과목목록.json`에 없는 **새 과목이면 필수**(학년 정수, 학기 `1` · `2`). 이미 있는 과목이면 생략하고, 적었는데 목록과 다르면 오류다.
- `meta.kind`(필수): `일반문제` · `모의고사` · `기출` · `단어집` 중 하나. 저장 폴더를 정한다.
- `meta.title`(필수), `meta.unit` · `meta.topic`(선택).
- `questions` · `terms` 중 하나는 비어 있지 않아야 한다. `kind`가 `단어집`이면 `terms`가 필요하다.
- 받지 않는 필드: `id` · `uploader` · `practice`(META, 문항 모두). 그 밖의 모르는 필드는 오류로 처리한다.
- 어떤 문자열에도 `registerPractice(`가 들어가면 안 된다(실행기의 종류 판별 규칙).
- 스키마는 `packages/core/src/upload/schema.ts`(zod)에 두고, 업로드 화면에 설명과 예시 JSON 내려받기를 제공한다.

### 8.2 제출과 검사

```
파일 N개 선택 → 제출 1건
  → 파일별 검사
      1) JSON 문법 · 스키마
      2) JSX로 변환(8.4) 후 check.js와 같은 규칙 (core 검사기)
      3) 기존 문제와 비슷한 문제 (--dup 과 같은 계산, 같은 과목)
      4) 이번 제출의 다른 파일끼리 비슷한 문제
  → 파일별 결과: 통과 / 경고 / 오류
  → 오류가 하나라도 있으면 제출되지 않는다(경고는 제출 가능, 관리자 화면에 함께 표시)
```

- 제한: 파일당 1MB, 제출 1건당 20파일, 사용자당 하루 제출 10건(설정값).
- 업로드 원문과 검사 결과는 DB(`upload_files`)에 저장한다. 승인 전까지는 콘텐츠에 보이지 않는다.
- 사용자는 "내 제출" 화면에서 파일별 상태(대기 · 승인 · 반려)와 반려 사유를 본다. 대기 중인 제출은 취소할 수 있다.

### 8.3 승인 (관리자만)

- 관리자 화면에서 제출 단위로 열고, 파일마다 승인 · 반려(사유 필수)를 고른다. 새 과목이면 "새 과목(N학년 N학기)" 표시가 붙고, 승인하면 같은 커밋에서 `과목목록.json`에 항목을 추가한다. 같은 새 과목을 다른 학년 · 학기로 적은 업로드가 이미 승인되어 있으면 오류로 보여 준다.
- 파일마다 미리보기를 제공한다(실제 풀이 화면으로 풀어 볼 수 있음).
- 승인을 확정하면 그 제출에서 승인한 파일들을 **커밋 하나**로 반영한다.
  1. `git pull --ff-only` (실패하면 중단하고 관리자에게 오류 표시)
  2. 파일 변환(8.4) 후 `<과목>/<kind>/`에 저장
  3. `git add -- <파일들>` → `git commit -m "업로드: <닉네임> — <과목> <제목> 외 N개"` (pre-commit 훅이 그대로 실행된다: check · 번들)
  4. 훅이 실패하면 커밋하지 않고 파일을 되돌린 뒤 훅 출력을 관리자 화면에 보여 준다. 업로드 상태는 대기로 남는다
  5. `git push`, 콘텐츠 새로고침
- 서버의 작업 사본에는 `git config core.hooksPath tools/hooks`를 설정해 둔다(15장).
- 관리자가 PC에서 GENERATE.md 흐름으로 커밋 · push하는 것과 서버 커밋이 같은 원격을 쓴다. 서버는 항상 pull 후 커밋하므로, push가 거절되면 다시 pull하고 한 번만 재시도한다.

### 8.4 JSON → JSX 변환

- 파일 경로: `<과목>/<kind>/<과목>_<제목>.jsx`. 제목의 공백은 `_`로, 파일명에 쓸 수 없는 문자는 지운다. 같은 이름이 있으면 `_2`, `_3`…을 붙인다(덮어쓰기 금지).
- 내용:
  ```js
  // 업로드: <닉네임>(<아이디>) · <승인 날짜>
  const META = { group: "운영체제", exam: "중간고사", unit: "4장", title: "스케줄링 OX 20문제", topic: "선점 · 비선점", uploader: "<아이디>" };
  const QUESTIONS = [
    { id: "u…", category: "…", question: "…", answer: false, explanation: "…" },
  ];
  const TERMS = [ … ];
  ```
- 값은 `JSON.stringify`로 쓴다(JSON 리터럴은 JS 리터럴이라 실행기 파서 규칙을 지킨다). 문항마다 고정 `id`를 붙인다(4장).
- 변환 결과를 core 파서로 다시 읽어 원래 JSON과 같은지 확인한 다음 저장한다.

## 9. 문항 신고 · 댓글

### 9.1 신고

- 풀이 화면과 결과 화면의 문항마다 "🚩 신고". 유형: `정답 오류` · `해설 오류` · `오타` · `중복` · `기타`, 설명(선택, 1000자).
- 신고할 때의 문항 내용(질문 · 정답 · 해설)을 함께 저장해 두어, 문항이 고쳐진 뒤에도 무엇을 신고했는지 알 수 있다.
- 관리자 화면: 열린 신고 목록 → `처리함`(메모) 또는 `기각`(사유). 실제 수정은 관리자가 git으로 한다(GENERATE.md 흐름). 고친 뒤 별칭 후보가 생기면 같은 화면에서 확정한다.
- 신고한 사람은 "내 신고"에서 상태와 메모를 본다.

### 9.2 댓글

- 문항별 댓글. 일반 텍스트만(HTML 이스케이프), 1000자 이내.
- **그 문항을 채점한 뒤에만** 보인다(풀이 화면 결과 단계, 결과 화면, 오답 분석). 풀기 전에 답을 보지 않게 하기 위한 화면 규칙이다.
- 본인은 수정 · 삭제, 관리자는 모든 댓글 삭제. 삭제는 표시만 지운다(`deleted_at`).
- 문항 ID 별칭이 확정되면 댓글도 새 ID로 보인다.

- 라우팅은 해시 없는 경로(`/2학년/2학기/중간고사/운영체제`, `/q/<세트 경로>` …). 서버는 모르는 경로에 `index.html`을 준다.
- 상태 관리는 `@preact/signals`. 서버 데이터는 화면별로 가져오고, 매니페스트만 `contentVersion` 기준으로 캐시한다.
- 화면 디자인은 기존 실행기의 배치와 색(카테고리 배지 색 규칙 등)을 따른다.

### 10.2 채점

- 채점 함수는 core에 하나만 둔다. 기존 규칙 그대로: 단답은 앞뒤 공백 제거 + 소문자화 + 연속 공백 1칸 후 정확 일치, 객관식은 인덱스(또는 보기 문구 일치), 단어 암기는 공백 · `.` · `,` · `-` · `_` 제거 후 비교.
- 브라우저(즉시 표시)와 서버(저장용 재채점)가 같은 함수를 쓴다.

### 10.3 연습 플러그인 호환 계층

- 기존 플러그인은 일반 `<script>`로 실행되며 실행기 전역을 쓴다. 이를 그대로 맞춰 준다.
  - 전역 제공: `registerPractice`, `escHtml`, `prRand` · `prInt` · `prNum` · `prMark` · `prClearMarks` · `prVec` · `prFact`, `SCHED_COLORS`, `currentSubject`, `currentPractice`, `practiceItems`, `practiceCats`, `practiceEmpty`. 구현은 기존 HTML에서 옮긴다(`apps/web/src/legacy/`).
  - 기존 `<style>` 중 연습 화면에 쓰이는 부분을 `legacy.css`로 옮겨 연습 화면에서만 적용한다.
  - 연습 문항 데이터(`<과목>/연습/**/*.jsx`)는 기존과 같은 방식으로 평가한다.
- 앱 시작 시 매니페스트의 플러그인을 경로 순으로 `<script>`로 불러온다(파일 간 의존 순서 유지). 연습 화면에 들어가면 `mount(root)`, 단축키는 `onKey` · `onEnter`로 넘긴다.
- 플러그인은 레포(운영자 커밋)에서만 온다. 업로드로 받지 않는다.
- 플러그인에는 시험 구분이 없다. `subject`가 맞는 과목의 **모든 시험 화면**(중간고사 · 기말고사)에 연습 메뉴 버튼이 나온다.
- 동작 확인: 플러그인 11개 각각 화면 진입 · 문제 생성 · 채점 · 단축키를 수동 점검표로 확인한다.

### 10.4 탐색 메뉴 · 과목 표시 설정

**탐색**
- 단계: 학년(`2학년` …, 맨 끝에 `미분류`) → 학기(`1학기` · `2학기`) → 시험(`중간고사` · `기말고사`) → 과목 카드. 위에 현재 위치(브레드크럼)가 있고 각 단계로 바로 돌아갈 수 있다.
- **선택지가 하나뿐인 단계는 건너뛴다.** 예: 보이는 학년이 2학년뿐이면 바로 학기 화면이 열린다. 브레드크럼에는 건너뛴 단계도 표시한다.
- **마지막 위치 기억**: 마지막으로 연 과목(시험) 화면 경로를 기기별(localStorage)로 기억해, 첫 화면에 "이어서: 2학년 2학기 중간고사 운영체제" 바로가기를 보여 준다.

**과목 표시 설정 (사용자별)**
- 설정 화면에 학년 · 학기별로 묶은 과목 목록과 과목마다 표시 스위치가 있다. 학기 묶음에는 "전부 표시 / 전부 숨김" 버튼이 있다.
- 서버에 저장한다(`user_subject_prefs`). 기기를 바꿔도 유지된다.
- 기본은 **표시**다. 새 과목도 모두에게 보이는 상태로 생긴다(설정 행이 없으면 표시).
- 숨긴 과목은 탐색 메뉴에서 빠지고, 남는 과목이 없는 시험 · 학기 · 학년 단계도 보이지 않는다.
- 숨김은 메뉴에만 적용된다. 리더보드(필터 없음)와 이미 쌓인 기록은 그대로이고, 주소로 직접 열면 "숨긴 과목" 표시와 함께 열린다.

## 11. 계정 · 인증

- 첫 관리자: 서버 CLI `pnpm --filter server admin:create`로 만든다.
- **초대 링크**: 관리자가 만든다(만료일, 최대 사용 횟수). 링크 = `/join/<토큰>`. 토큰은 32바이트 랜덤, DB에는 해시만 저장. 언제든 폐기할 수 있다.
- **가입**: 초대 링크로 접속 → 아이디(영문 소문자 · 숫자 · `_`, 3~20자, 바꿀 수 없음) · 닉네임(2~16자, 중복 불가, 바꿀 수 있음) · 비밀번호(8자 이상) → 바로 로그인.
- **로그인**: 아이디 + 비밀번호. 비밀번호는 argon2id. 같은 IP · 아이디의 연속 실패는 속도 제한.
- **세션**: `sessions` 테이블 + 쿠키(`HttpOnly` · `Secure` · `SameSite=Lax`, 30일, 쓸 때마다 연장). 변경 요청(POST · PATCH · DELETE)은 `Origin` 헤더가 설정된 출처와 같아야 받는다.
- **비밀번호 재설정**: 이메일이 없으므로 관리자가 계정 화면에서 재설정 링크(1회용, 24시간)를 만들어 직접 전달한다.
- **권한**: `admin` · `member`. 관리자 API는 `admin`만. 정지된 계정은 로그인할 수 없고 리더보드에서 빠진다.

## 15. 빌드 결과물 · 실행 설정

호스팅 방식은 운영자가 정한다. 프로그램은 다음만 제공한다.

- `apps/web` → `pnpm --filter web build` → `apps/web/dist/` (정적 파일). API와 같은 출처에서 서비스하는 것을 전제로 한다(쿠키 · `Origin` 검사). 다른 출처로 띄우면 `PUBLIC_ORIGIN`과 CORS 설정이 필요하다.
- `apps/server` → `pnpm --filter server build` → `node dist/index.js`. 원하면 `WEB_DIST`를 지정해 서버가 정적 파일까지 서비스할 수 있다.
- 환경 변수

  | 이름 | 뜻 |
  |---|---|
  | `PORT` | API 포트 |
  | `DATABASE_PATH` | SQLite 파일 경로 |
  | `CONTENT_DIR` | 콘텐츠 작업 사본(이 레포 clone) 경로 |
  | `CONTENT_BRANCH` | 콘텐츠 브랜치(이미지 기본 `master`, 개발 샌드박스는 `main`) |
  | `GITHUB_WEBHOOK_SECRET` | webhook 서명 검증용 시크릿(3.2) |
  | `PUBLIC_ORIGIN` | 서비스 주소(쿠키 · `Origin` 검사) |
  | `WEB_DIST` | (선택) 정적 파일 경로 |
  | `GIT_AUTHOR_NAME` · `GIT_AUTHOR_EMAIL` | 서버 커밋 작성자 |
  | `UPLOAD_MAX_FILE_BYTES` · `UPLOAD_MAX_FILES` · `UPLOAD_DAILY_LIMIT` | 업로드 제한 |

- 작업 사본 준비: clone → `git config core.hooksPath tools/hooks` → push 권한(배포 키 등) → GitHub 레포에 webhook 등록(3.2). 작업 사본에서 직접 파일을 고치지 않는다(pull이 막힌다). 훅이 node를 쓰므로 서버에 node가 있어야 한다(서버 자체가 node라 충족).
- 백업 대상은 SQLite 파일 하나(문제 내용은 git에 있다).

## 16. 기존 기록 이전 (요청 시)

- 운영자가 요청할 때만 한다. 대상은 기록 레포의 `logs/<기기>/<YYYY-MM>.jsonl`.
- 이벤트 `run`을 세션으로 바꾼다: `partial: 1`이면 `partial`, 아니면 `set`. 문항 키(`weakQKey` = `<파일>#<해시>`)의 `<파일>` 부분을 v2 세트 경로로 맞춘다(옛 키의 파일 표기가 저장 키인지 파일명인지 이전할 때 확인).
- 옛 기록에는 학생 답 원문이 없으므로 `raw_answer`는 비우고 `correct`만 옮긴다. SRS 카드는 옮긴 세션을 시간순으로 재생해 만든다.
- `pick`은 `pinned_items`, `reset`은 `analysis_resets`, `legacy` 덩어리는 문항별 횟수만 있고 시각이 없으므로 오답 분석용으로만 옮기고 리더보드 · SRS에는 넣지 않는다.
- 스크립트: `apps/server/scripts/import-legacy.ts --user <아이디> <logs 폴더>`. 먼저 `--dry-run`으로 건수와 매칭 안 된 키를 보고한다.

## 18. 확정된 세부 사항

- `partial` 세션(틀린 문제 다시 풀기 등)은 오답 분석에만 넣고 리더보드 · SRS에서 뺀다(5.2).
- 관리자가 승인 전에 업로드 내용을 직접 고치는 기능은 넣지 않는다. 고칠 점이 있으면 반려하고 다시 올리게 한다.
- 원격의 새 커밋은 GitHub webhook으로 받는다(3.2). 수동 새로고침은 예비 수단으로 남긴다.
- 학년 · 학기는 `과목목록.json`, 시험은 세트 META `exam`(3.4). 학기는 1 · 2학기만, 용어집은 시험별, 새 과목은 기본 표시.
- 연습 플러그인은 그 과목의 모든 시험 화면에 나온다(10.3). 오늘의 복습 · 오답 분석은 시험별이다(5.3 · 7장).
